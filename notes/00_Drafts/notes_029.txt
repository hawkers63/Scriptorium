**Subject:** Bug Hunter Report — Backend Retry Transport and Sudden Network Loss

## Executive Summary

This report analyses the backend retry-transport mechanism in `scriptorium.py`, with a particular focus on the handling of sudden network connectivity loss during active generation requests. The transport functionality is shared between the Claude and Ollama backends through the methods `_request_json_with_retries()` and `_request_with_retries()`. The underlying logic is robust, well-defined, and designed to be fail-safe. In the event of a sudden disconnection during a request generation, the system categorises the incident as a retryable transient network fault, triggered by socket-level exceptions such as `TimeoutError`, `ConnectionError`, `urllib.error.URLError`, or `http.client.HTTPException`. The system is configured to attempt the request up to a maximum of three times, employing bounded exponential backoff and jitter, whilst also allowing for cancellation support, enabling users to interrupt any in-progress wait via the user interface. Should connectivity not be restored within this timeframe, a specific `BackendError` is raised and communicated to the user.

## Identified Behaviour on Sudden Connectivity Loss

1. **Request Initiation**
   The methods `process()` or `process_selection()` initiate a worker thread that subsequently calls `run_backend()`. This method forwards the user input to either `call_anthropic()` or `call_ollama()`, both of which create a new `urllib.request.Request` through a `request_factory()` callable and then delegate to `_request_json_with_retries()`.

2. **Per-Attempt Handling**
   Within `_request_with_retries()`, a new request is initiated for each attempt within a context managed by `with urllib.request.urlopen(..., timeout=...)`. If the network connection is interrupted after the connection has been established but before the complete response is received, the error typically manifests as:
   - `TimeoutError` (socket timeout),
   - `ConnectionError` / `ConnectionResetError` (the server or proxy has abruptly terminated the connection),
   - `urllib.error.URLError` (issues such as DNS failure or connection refusal),
   - `http.client.HTTPException` (for example, `IncompleteRead` or `RemoteDisconnected`).

3. **Retry Decision**
   The single exception handling branch for `(urllib.error.URLError, TimeoutError, ConnectionError, http.client.HTTPException)` within `_request_with_retries()` captures all these occurrences. If the current attempt is not the final one (`attempt < MAX_REQUEST_ATTEMPTS - 1`), the code:
   - Calculates a bounded exponential backoff delay with added jitter,
   - Invokes `on_retry(...)` (if defined) to update the status bar,
   - Waits via `_wait_for_retry(delay, cancel_event)`,
   - Reinitiates the process with a fresh request factory to ensure that a partially transmitted request body is not corrupted or inaccurately replayed.

4. **Cancellation During the Retry Wait**
   The method `_wait_for_retry()` employs `threading.Event.wait(delay)` when a cancellation event is provided. If the user opts to Reject, Clear, imports a new file, or closes the window, the method `_invalidate_inflight()` sets the current request's cancellation event. The worker thread is then awakened immediately, raising `RequestCancelled` (a subclass of `BackendError`), and no further attempts are made.

5. **Exhaustion and Failure Reporting**
   In instances where all attempts fail, the code raises:

   ```python
   BackendError(f"Could not reach {label}: {reason}{hint}")
   ```

   Here, `reason` details the final exception encountered, and `hint` provides backend-specific connectivity advice (e.g., "Is Ollama running at localhost:11434?"). This error is captured by the worker's `except BackendError` clause and communicated to the user interface via `_post_to_ui(_on_error, ...)`, which clears the busy state and presents an error dialog.

## Boundaries and Edge Cases Observed

- **Distinct Treatment of HTTP Error Responses.** A `URLError` or HTTPException indicating a lost connection will trigger a retry, whereas a completed HTTP error response (4xx/5xx) will only be retried if its status code is included in the backend's `transient_statuses` set. Otherwise, it will fail immediately, as this correctly reflects that the server has received the request and provided a definitive response.

- **Non-JSON Responses Are Not Retried.** A successful 200 response that cannot be interpreted as JSON will raise a `BackendError` within `_read_json_response` and will not be retried. If a network interruption results in an *empty* 200 response, the system could theoretically receive a non-JSON body instead of a socket exception, thus preventing a retry. The current design presumes that a truncated body, which still conforms to valid HTTP, indicates a server-side issue rather than a transient network fault. This approach has been consciously adopted in the existing implementation.

- **No Per-Attempt Time Budget Beyond Socket Timeout.** The retry loop limits only the number of attempts, not the total elapsed time. A user experiencing a network drop longer than two backoff periods (each capped at `MAX_RETRY_DELAY = 10s`) will receive a final error notification; the system will not become unresponsive indefinitely.

- **User Interface Remains Responsive.** The socket waits and backoff periods operate on a daemon worker thread, ensuring that Tk remains unblocked. Progress on retries is communicated to the status bar only while the request ID aligns with the current UI request.

## Recommended Follow-up (Analysis Only – No Code Changes Proposed)

At present, no code modifications are necessary for the described "sudden loss" scenario under the existing design framework. An optional enhancement could involve evaluating whether an empty or truncated 200 response that fails JSON parsing should prompt a single retry. However, this would require a deliberate product decision, as retrying an identical request may incur additional costs on the server side.
