1. UI/UX Audit & Visual Hierarchy Breakdown

Overall state

Scriptorium already has a sound Windows 11 dark-mode foundation: CustomTkinter dark mode, the blue default accent, a dual-pane centre, modal settings, a compact tone picker, a two-row action area, and a status bar. The most important recent repairs are visible in the current code: Original and Revised now share the same dark surface constants, the Revised pane uses tk.Text specifically for reliable diff tags, the notice banner is a real frame with a Dismiss button, Settings has a scrollable body and a fixed bottom button row, and the Processing state includes both disabled controls and an indeterminate progress bar.

The remaining visual issue is not that the interface lacks features. It is that the hierarchy is still quite flat: toolbar controls, review actions, secondary file operations, status text, and review notices all compete at similar visual weight. At 1180x760 this is serviceable; at the 920px minimum it risks looking compressed and slightly ad hoc, especially because row packing uses fixed-width buttons and side packing rather than responsive grid allocation.

Dual-pane layout and typography

Current implementation:
- `PANE_BG = "#1e1e1e"`, `PANE_FG = "#e6e6e6"`, `PANE_FONT = ("Segoe UI", 13)`.
- `self.original_box` is a `ctk.CTkTextbox` with matching foreground/background/font.
- `self.revised_box` is a `tk.Text` with `padx=12`, `pady=12`, `spacing1=4`, `spacing3=6`.
- `self.original_box` does not currently receive explicit inner padding or paragraph spacing in the same way as `self.revised_box`.

Assessment:
The panes are visually closer than earlier versions, but not yet fully matched. Tk text widgets and CTk textboxes render internal padding and line metrics differently unless explicitly harmonised. Revised currently has clear 12px internal padding and paragraph spacing, while Original relies on CTk defaults. That can produce a subtle but noticeable mismatch: the left text may begin at a slightly different x/y offset than the right text, and paragraph rhythm can differ between editing and review.

Recommendation:
Use named pane metrics and configure both panes around the same cadence:
- Outer pane frame padding: 12px left/right, 10px top.
- Inter-pane gutter: 12px total, 6px each side.
- Header row bottom gap: 6px.
- Text inset: 14px horizontal, 12px vertical.
- Font: Segoe UI 13 for text at 100%, with a future option to let CTk scaling handle DPI instead of viewport-based font changes.
- Paragraph rhythm: 4px before and 7px after paragraphs for both text widgets where supported.

Visual diff highlighting and contrast

Current implementation:
- `DIFF_INS_FG = "#5ee0c8"` gives approximately 10.3:1 contrast against `#1e1e1e`.
- `DIFF_DEL_FG = "#ffa0a8"` gives approximately 8.61:1 contrast against `#1e1e1e`.
- Insert and delete tags use both foreground and background fill, which is the correct direction for scanning long prose.

Assessment:
The current colours exceed WCAG AA for normal text. The issue is less strict contrast and more semantic separation. The insert colour is cool/green and attractive, but quite saturated. The delete colour is readable, but overstrike plus a filled red background can become noisy in dense replacements. In Inline view, replacements show deleted source immediately followed by inserted wording, so the system needs enough contrast to distinguish state while preserving a calm reading experience.

Recommendation:
Keep word-level diff as the default because it is aligned with prose review. Character-level diffs should be reserved for an optional micro-diff mode later, since they often overemphasise punctuation and morphology in natural language. Improve the current palette by using slightly softer foregrounds with darker, lower-chroma fills:
- Insert foreground: `#7ee0c3` against `#1d1e1e`, approximately 10.61:1.
- Insert background: `#12342d`.
- Delete foreground: `#ffb3ba` against `#1d1e1e`, approximately 9.87:1.
- Delete background: `#3a1d24`.
- Active change outline: `#d6e4ff`, using underline plus a subtle background lift rather than underline only.

Clean view:
Clean view should remain visually quiet. It should show the final text with inserted/replaced revised wording marked as "changed", but pure deletions have no visible span. This is conceptually correct, but the change navigator may land on a zero-width range for pure deletions. The status bar should explicitly say "deletion only at cursor" or the navigator label should show "deleted text hidden in Clean view" when the active range is zero-width.

Inline view:
Inline view is best for review and audit. Deleted text should remain red with overstrike, but a small x-offset or spacing rule is not available in tk.Text. The most practical improvement is to render replacements as:
deleted text tagged `deleted`, then inserted text tagged `changed`, with no extra punctuation inserted by the renderer. Preserve this behaviour, but make the active replacement easier to find by adding a second tag such as `active_change` with a background/underline combination.

Toolbar and action bar harmony

Current implementation:
- `_build_toolbar()` uses one grid row with Mode, Strength, Role, Tone and Preset.
- Settings has already been moved out of the toolbar into row 2 of the bottom action area.
- `_build_actionbar()` uses two packed rows. Row 1 contains Process, Softer, Stronger, Accept, Reject, Copy revision, Copy summary, Undo, Clear, Import, Export. Row 2 contains Paste, Copy, History, Copy rich diff, Export diff, Settings.

Assessment:
The current split solves the most urgent overlap, but the two rows still mix workflow hierarchy. The first row has the right priority in spirit: generate/review actions first, file operations right. The second row works as utility space. At the 920px minimum, however, fixed widths and side packing can still become brittle if font scaling, translated text, or Windows DPI changes expand widget requests. The row also uses text-only controls where icon+text or short labels would improve scanning.

Recommendation:
Keep two rows, but make them grid-based with explicit groups:
- Row 1 left group: Process, Softer, Stronger.
- Row 1 centre group: Accept, Reject.
- Row 1 right group: Clear, Import, Export.
- Row 2 left group: Paste, Copy original, History.
- Row 2 centre group: Copy revision, Copy summary, Copy rich diff, Export diff.
- Row 2 right group: Settings.

At 920px width, hide no controls; instead shorten labels:
- `Copy original` can display as `Copy`.
- `Copy revision` can display as `Copy revision`.
- `Copy summary` can display as `Summary`.
- `Copy rich diff` can display as `Rich diff`.
- `Export diff...` can display as `Export diff...`.

Recommended button widths:
- Primary: Process 112px, Accept 104px.
- Nudge controls: 82px each.
- Destructive/reject neutral: 86px.
- Clipboard/file utilities: 88-118px depending label.
- Settings: 104px.
- Horizontal gap inside groups: 6px.
- Horizontal gap between groups: 14px.
- Action bar row vertical gap: 6px.

Interactive states and micro-feedback

Current implementation:
- `_set_busy()` disables Process, Accept, Softer and Stronger.
- It packs a 4px indeterminate progress bar and pulses the Process button between `BUSY_BLUE` and `BUSY_BLUE_DARK` every 400ms.

Assessment:
This is a good base. The motion is meaningful because it shows the app is alive during a backend request. The main risk is that the busy state has only one animated element and the status label may remain text-heavy. Users benefit from a short phase label: preparing request, waiting for backend, retrying, rendering revision.

Recommendation:
Add a compact busy/status strip style:
- Progress height: 4px, unchanged.
- Progress colour: CTk default blue or `#2f81c7`.
- Status text while busy: begin with `Working...` followed by a concise phase.
- Pulse interval: 500-650ms instead of 400ms for a calmer Windows 11 feel.
- Disable only controls that can corrupt request state. Continue allowing Copy Original and History if safe; keep Process/Accept/Nudge disabled.

Ambiguity and notice banner

Current implementation:
- Notice banner uses `AMBER_BG = "#43361f"`, `AMBER_FG = "#f5d589"`, `AMBER_RULE = "#c9a227"`.
- It appears above the status bar, with title `Review notices (not silently changed)`, bullet lines, and a `Dismiss` button.

Assessment:
This is directionally strong. The content is honest and safety-minded. The current amber background has enough contrast, but the banner can still read as a dense warning block. The Dismiss affordance is text-only and the title/body are combined into one label, so hierarchy is limited.

Recommendation:
Split title and body into two labels and right-align a compact close button. Use a darker background with a brighter rule:
- Notice background: `#27200f`.
- Notice border/rule: `#d6a529`.
- Notice title: `#ffe3a3`.
- Notice body: `#f4d06f`.
- Dismiss button: width 32, text `X`, `fg_color="#3a3324"`, `hover_color="#4a402c"`.
- Corner radius: 6px.
- Padding: outer x 12, y 6; body x 12, y 8.

Dialog UX polish

SettingsDialog:
Current Settings ergonomics are fairly good: modal grab, Escape binding, centred over parent after idle, resizable vertically, scrollable content, fixed Save/Cancel row. Remaining polish opportunities are mostly focus and form alignment:
- Set initial focus to the backend segmented control if no backend is selected; otherwise to the first enabled field.
- Bind Return in the API key/model entries to Save where appropriate.
- Make the body content width responsive within the dialog rather than relying on fixed 480px entry widths.
- Align checkbox text with multi-line wrapping to avoid long labels clipping at 150-200% DPI.
- Consider `self.wait_visibility()` before `grab_set()` to reduce rare focus edge cases on Windows.

TonePickerDialog:
The tone picker is compact and understandable. It already gives non-blocking feedback for selection limits and conflicts. Improvements:
- Make it vertically resizable with a minimum of 420x420; keep current 420x540 default.
- Put Apply/Cancel in a fixed bottom row, outside the scrollable tone list.
- Set focus to the first selected tone or Apply button after construction.
- Add Return binding to Apply and Escape to Cancel/destroy.
- Use a title label, supporting line, scroll list, status, and fixed action row with consistent 16-18px margins.

Snippet F: calmer busy pulse

Update `_set_busy()` and `_pulse_process()`:

```
def _set_busy(self, flag):
    """Disable request-changing controls while a backend call is running."""
    self.busy = flag
    self.process_btn.configure(
        text="Working..." if flag else "Process",
        state="disabled" if flag else "normal")
    self.accept_btn.configure(state="disabled" if flag else "normal")
    self.softer_btn.configure(state="disabled" if flag else "normal")
    self.stronger_btn.configure(state="disabled" if flag else "normal")

    if flag:
        self.progress.pack(fill="x", padx=12, pady=(0, 4),
                           before=self.status)
        self.progress.start()
        self._pulse_job = self.after(600, self._pulse_process)
    else:
        if self._pulse_job is not None:
            self.after_cancel(self._pulse_job)
            self._pulse_job = None
        self.process_btn.configure(fg_color=["#3a7ebf", BUSY_BLUE])
        self.progress.stop()
        self.progress.pack_forget()

def _pulse_process(self):
    """Alternate the Process button blue so a long call still feels alive."""
    if not self.busy or not self.winfo_exists():
        return
    current = self.process_btn.cget("fg_color")
    dark = current[1] if isinstance(current, (list, tuple)) else current
    next_colour = BUSY_BLUE_DARK if dark != BUSY_BLUE_DARK else BUSY_BLUE
    self.process_btn.configure(fg_color=next_colour)
    self._pulse_job = self.after(600, self._pulse_process)
```

def _focus_initial_control(self):
    """Place keyboard focus on the first useful Settings control."""
    if not self.winfo_exists():
        return
    backend = BACKEND_IDS.get(self.backend_var.get())
    try:
        if backend == "anthropic":
            self.key_entry.focus_set()
        elif backend == "ollama":
            self.ollama_combo.focus_set()
        else:
            self.save_btn.focus_set()

This avoids grabbing before the top-level is visible, while keeping the same modal behaviour.

Snippet H: TonePickerDialog resizable polish

```

```

to:

```

```

After the Apply button is created, add:

```
self.bind("<Return>", lambda _event: self._apply())
self.after_idle(self._focus_initial_control)
```

Then add:

```
def _focus_initial_control(self):
    """Focus the selected tone list first, falling back to Apply."""
    if not self.winfo_exists():
        return
    try:
        for tone in self.selected_order:
            variable = self.variables.get(tone)
            if variable is not None:
                self.focus_set()
                return
        self.focus_set()
    except tk.TclError:
        pass
```

This is intentionally conservative. A richer version would retain references to each checkbox and focus the first selected checkbox directly, but that requires a slightly wider refactor of the checkbox creation loop.

Final judgement

The interface is already functionally mature. The next visual lift should avoid a redesign and instead tighten the system: one named palette, equal pane typography, grouped controls, calmer motion, and modals that feel deliberately placed and keyboard-friendly. These changes are small enough to implement incrementally while making the app feel more cohesive, especially at the 920px minimum width and on high-DPI Windows laptops.
