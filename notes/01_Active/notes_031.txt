2.1 A — Make the existing Explorer drop feature discoverable
-----------------------------------------------------------
User journey:
  Open Scriptorium with an empty Original pane -> see a short import hint
  in the existing Original heading -> drop one .txt, .md or .docx file ->
  normal shared loader -> inspect Original -> Process -> review revision.

Use the current heading, not text inserted into the editor. Suggested
empty states are "Original · drop a file or paste text" when the native
hook is installed and "Original · paste text or use Import…" otherwise.
Once the pane has content, return the heading to "Original". This avoids
accidentally sending placeholder instructions to the model or including
them in word counts. Any non-empty buffer, including spaces, hides the
hint; it is guidance for an empty editor, not content detection.

State: retain the CTkLabel as self.original_heading. Derive its text from
the live buffer and the existing _drop_old_wndproc installation state.
Configuration: none. Performance: reuse the Original string that
_refresh_status() already reads; no new polling or file access.
Layout: retain the existing row, padding and font. Check the longest
heading at 920x600 and 1180x760, at 100%, 125%, 150% and 200% Windows
scaling. Do not shrink the text or move the accepted action-bar groups
merely to accommodate this optional hint.

Native architecture to preserve:
  - shell32/user32 ctypes declarations and pointer-sized WNDPROC types;
  - SetWindowLongPtrW/SetWindowLongW on the existing toplevel;
  - CallWindowProcW forwarding for messages that are not consumed;
  - a strong Python reference to the callback until teardown;
  - DragQueryFileW Unicode path extraction and DragFinish in finally;
  - plain Python queued events from WNDPROC, drained by the Tk poller;
  - Original-descendant hit-testing and the one-file extension filter;
  - confirmation before a successful drop replaces populated Original;
  - restoration of the old procedure before the window is destroyed.

Microsoft documents the WM_DROPFILES handle, zero return for a processed
message, and DragFinish cleanup. The existing implementation supplies
these pieces; DragAcceptFiles alone would not implement the full path.
Sources: [WM_DROPFILES](https://learn.microsoft.com/en-us/windows/win32/shell/wm-dropfiles),
[DragFinish](https://learn.microsoft.com/en-us/windows/win32/api/shellapi/nf-shellapi-dragfinish),
[SetWindowLongPtrW](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setwindowlongptrw).

Project-specific critical constraint: never call Tk, including after(),
after_idle() or winfo_containing(), inside the native WNDPROC. ROADMAP.md
1394–1458 records the fatal re-entrancy failure and its queue/poller fix.
The hint refresh belongs in ordinary Tk callbacks, never in that hook.
No cross-integrity message-filter bypass is proposed. A successful hook
does not establish that an elevated app can receive an Explorer drop.

The current loader performs file reading on Tk's thread. That could pause
the interface for a large or slow document, but no such pause was measured
here. Moving it to a worker would require a separate load identifier,
captured editor state, and an explicit policy for edits made while reading.
Do not introduce that larger change just to add this hint. Word stays an
optional python-docx path and retains the current table-content refusal.

Acceptance:
  - Empty/populated/Clear/Undo states show the appropriate heading.
  - A forced hook-install failure leaves an accurate Import/paste hint.
  - A genuine Explorer drop still works in source and packaged builds.
  - A cancelled replacement, unsupported path and missing python-docx leave
    editor contents, undo history and in-flight work unchanged.

Existing "(none)" remains a no-op. Returning controls manually to a saved

Acceptance:
  - Each individual control change clears a selected preset when needed.
  - Apply changes all fields before comparison; the intended name survives.
  - Merely opening/cancelling Tone Picker leaves an exact match selected.

2.4 D — Strengthen roles, then evaluate one role and one tone
------------------------------------------------------------
The strongest rewriting improvement is to tighten specific role wording
before lengthening the menus. Several current phrases warrant calibration:
  - Executive foregrounds "decisions and clear next steps".
  - Project Manager ends on "unambiguous next actions rather than open
    questions". A source that asks a question must be allowed to keep it.
  - Client Relations favours a "reassuring" register. A courteous rewrite
    must not add a promise, apology, assurance or solution.
The global rules already prohibit invented facts. These phrases create
possible competing instructions; this review has not measured new failures.

D1. Replace only those three role descriptions with bounded alternatives.
Also state one common hierarchy in build_system_prompt's non-negotiable
rules: preserve meaning/protected content first; obey the selected mode
next; apply role and tones within that remit. Correct must stay minimal
even with Substantial strength and a strongly styled role/tone selected.
This rule applies with zero, one, two or three tones, complementing the
three-tone-only explicit hierarchy already in build_tone_instruction.

Do not solve the problem by deleting all role/tone controls in Correct,
changing default controls, or adding an automatic second call. Those are
different behaviour changes. A single request still produces one suggested
revision, ambiguities and a note, followed by explicit human review.

D2. Candidate role: Personal Correspondence.
Purpose: letters and emails from one person to another, where Executive
or Client Relations can introduce an unnecessarily organisational register.
It preserves first/second person, stated relationship, greetings/sign-offs
already present and the writer's actual level of formality. It cannot infer
intimacy, emotions or biographical details. It contains no samples, identity
profile, learned style or permanent author brief. It is a task context.
Compare against (none)+Friendly/Diplomatic and Client Relations before
adding it. If those already work as well, a saved preset is sufficient.

D3. Candidate tone: Firm.
Purpose: retain a clearly stated refusal, limit or condition without
turning it into a tentative suggestion or surrounding it with concessions.
Example source: "I cannot agree to the revised fee. I can discuss the
original quotation on Friday." The fee refusal, offer to discuss and
Friday must survive; no threat, deadline, apology or offer is added.
Compare against Direct+Diplomatic and Confident+Concise. Firm is worth a
new menu entry only if Mark finds a repeatable difference in preserving
boundaries. It must never turn "may" into "will" or a question into an order.
Keep it compatible with Empathetic and Diplomatic unless evidence proves
a real contradiction. Do not add speculative hard-conflict pairs.

Both candidates are shown behind FALSE release constants in section 3.
These are developer calibration switches, not new Settings controls.
They are not a way to bypass calibration by enabling a feature in config.
If adopted, add each to the existing canonical table before derived lists
are built. Stored presets continue to contain role/tone names, so no
schema change is necessary. A pack using a new name needs a sufficiently
new app: older normalisation can drop an unknown role or unknown tone.
Do not promise lossless backwards compatibility with an older executable.

No live calls were made for this note. Static wording cannot guarantee

  4. A complaint with no apology, compensation offer or assurance.

2.6 F — Respect long Retry-After values without lengthening the wait
------------------------------------------------------------------
Keep the existing shared transport, three-attempt limit, bounded
exponential backoff with jitter, HTTPError-before-URLError ordering,
request factories, cancellation events and per-backend status sets.
Keep malformed JSON and authentication failures outside automatic retry.
Neither a new SDK nor a new HTTP dependency is required.

Observed case:
  _retry_after_seconds({'Retry-After': '120'}) returns 30.0 today.
  Therefore a retryable 429/503 can be retried 90 seconds before the
  server's requested delay ends. This was reproduced without networking.

Proposed policy: parse the server delay without shortening it. For a
valid delay of 0–30 seconds, use the current cancellable wait. For a
longer valid delay, stop this logical request with an actionable message
and make no automatic follow-up attempt. Keep 30 seconds as the automatic
wait budget, not as a rewrite of the server's delay. Mark may try again
later. This does not schedule a background wake-up or reserve a future
request, and it does not block a deliberate new Process action.

Accept RFC integer delay-seconds or an HTTP date; reject malformed,
non-finite and oversized header text. Negative/fractional numeric strings
are invalid delay-seconds under this proposal and use ordinary fallback
backoff. A past valid date produces a zero wait. Explain that parser
behaviour change in tests; the current helper accepts floats.
Source: [RFC 9110, section 10.2.3](https://www.rfc-editor.org/rfc/rfc9110.html#section-10.2.3).

The helper can now raise BackendError. Close the HTTPError response in
finally around the delay calculation, so the new stop path cannot leak
the response. No change to API payloads, token limits, endpoints or
backend selection. The final existing error path still carries request-id
when available. The long-delay message is a local retry-policy outcome.

Claude documents 429 rate limiting and 529 overload; not every 429 is
necessarily a brief transient event. A missing header alone is not enough
to diagnose a spend limit. Keep current bounded attempts unless a reliable
documented error classification is separately implemented.
Source: [Claude API errors](https://platform.claude.com/docs/en/api/errors).

Transport limits to state honestly: Event.wait cancellation stops backoff
and future attempts; it cannot forcibly stop an already-blocked urllib
socket or guarantee that the server did no work. A retried POST following
a lost response can duplicate generation work and cost. A socket timeout
is not a guaranteed overall wall-clock deadline for an entire request.
Do not present a simple 3 x timeout calculation as a strict upper bound.

Streaming preparation remains sufficient for now: response_reader is the
existing extension point, but transparent retries require it to have no
visible partial-output side effects. Ollama streams NDJSON and can report
an error inside an already-started stream. Claude can likewise report
errors after the initial successful HTTP response. A future design needs
backend-specific framing and an explicit partial-result policy; it cannot
just append transport chunks to the revision pane or feed each chunk to
json.loads. Mark's decisions about showing/keeping partial drafts remain
pending, so visible streaming is not proposed for implementation here.
Sources: [Ollama streaming](https://docs.ollama.com/api/streaming),
[Ollama errors](https://docs.ollama.com/api/errors),
[Claude API errors](https://platform.claude.com/docs/en/api/errors).

Acceptance by fault injection, with no paid calls:
  - 429/503 followed by success; persistent transient errors stop at three.
  - A 120-second hint makes one attempt and stops; response is closed.
  - Numeric 0/1/30, long delays, future/past HTTP dates, malformed text,
    empty header, NaN/infinity, negative and fractional strings.
  - Cancel before attempt, during short backoff and before a later attempt.
  - 401/403/404 and successful-HTTP malformed JSON are not retried.
  - Connection reset still follows existing retry/cancellation behaviour.
  - No late completion or retry status overwrites a newer request/history.

3.2 B — Preset comparison without automatic persistence

```python
def preset_control_signature(preset):
    """Compare controls in order while retaining a legacy voice reference."""
    clean = normalise_preset(preset)
    if clean is None:
        return None
    return (
        clean["mode"], clean["strength"], clean["role"],
        tuple(clean["tones"]), preset.get("voice"),
    )
```

METHOD B2 — add to Scriptorium:
```python
def _queue_preset_check(self, *_args):
    """Compare after all fields of a preset application have settled."""
    if not hasattr(self, "preset_var"):
        return
    if getattr(self, "_preset_check_job", None) is None:
        self._preset_check_job = self.after_idle(self._check_preset_match)


def _check_preset_match(self):
    """Clear a saved label when the current controls no longer match it."""
    self._preset_check_job = None
    expected = preset_control_signature(
        resolve_preset(self.cfg, self.preset_var.get())
    )
    if expected is None:
        return
    current = preset_control_signature({
        "mode": self.mode_var.get(),
        "strength": self.strength_var.get(),
        "role": self.role_var.get(),
        "tones": list(self.selected_tones),
        "voice": self.active_voice,
    })
    if current != expected:
        # The stored preset and completed revision remain untouched.
        self.preset_var.set("(none)")
```

```python
def _retry_after_seconds(headers):
    """Parse a finite server delay without shortening a valid request."""
    value = headers.get("Retry-After") if headers else None
    if not isinstance(value, str) or len(value) > 128:
        return None
    value = value.strip()
    if not value:
        return None
    try:
        if re.fullmatch(r"[0-9]+", value):
            delay = float(value)
        else:
            retry_at = parsedate_to_datetime(value)
            if retry_at.tzinfo is None:
                retry_at = retry_at.replace(tzinfo=timezone.utc)
            delay = retry_at.timestamp() - time.time()
    except (TypeError, ValueError, OverflowError):
        return None
    if not math.isfinite(delay):
        return None
    return max(0.0, delay)


def _retry_delay(failure_index, headers=None):
    """Choose bounded backoff, or stop when the server asks for longer."""
    retry_after = _retry_after_seconds(headers)
    if retry_after is not None:
        # MAX_RETRY_AFTER now caps automatic waiting, not the server hint.
        if retry_after > MAX_RETRY_AFTER:
            seconds = math.ceil(retry_after)
            raise BackendError(
                f"The server asked for a pause of about {seconds} seconds. "
                "This request has stopped without another automatic "
                "attempt. Wait for that interval, then try Process again."
            )
        return retry_after
    exponential = BASE_RETRY_DELAY * (2 ** failure_index)
    jitter = secrets.randbelow(251) / 1000
    return min(exponential + jitter, MAX_RETRY_DELAY)
```
