2.1  Bug 1 — Stale or cancelled requests can still reach the UI      HIGH
     Location: process() (819–860), _on_success() (862–895),
               _on_error() (897–901), _revision_is_stale() (903–905),
               _on_diff_view_change() (907–912), accept() (914–927),
               copy_revision() (937–942), export_file() (977–998).

     (a) Second-request case. process() sets self._processing_source to
     the text it is about to send, then starts a daemon thread.
     self.last_result is only replaced later, inside _on_success. Accept,
     Copy and the Clean/Inline toggle all read _processing_source as if it
     were "the text last_result was built from". That is true only until a
     second request starts:
         1. Process text A -> last_result is A's revision;
            _processing_source == A.
         2. Edit the box to B (or just click Process again on A) ->
            process() immediately overwrites _processing_source with B,
            before the first worker has returned.
         3. last_result is still A's revision.
         4. _revision_is_stale() compares the box (B) to _processing_source
            (also B) -> returns False. Accept overwrites B with A's
            revision with no warning; Copy silently clipboards A's
            revision; the Inline toggle diffs A's revision against B,
            producing nonsense highlighting.

     (b) Dismiss-during-busy case (not previously reported). None of
     Reject, Undo, Clear or Import check self.busy, and process()'s worker
     callback is unconditional:
         1. Click Process for text A. While the request is in flight,
            click Clear (or Undo, or Import a different file B).
            reject() runs, clearing last_result and the revised pane —
            the user has explicitly moved on.
         2. The request for A completes. self.after(0, self._on_success,
            A, ph_map, result) fires regardless. _on_success sets
            self.last_result = result and calls render_diff() for A,
            repainting the pane the user just cleared. It does add a
            "text changed while processing" warning to the ambiguity
            strip, but that strip looks identical to a normal ambiguity
            note and is easy to miss — the practical effect is a revision
            for content that is no longer on screen reappearing
            unannounced.

     Verified: this is a direct trace of the code above; both paths are
     deterministic from the source, not conjecture.

     Remedy: a single monotonic request id, checked once at the top of
     _on_success/_on_error, plus a `busy` guard on the action buttons.
     See Fix 1.


2.2  Bug 2 — A corrupt OR merely non-object config file crashes the
     app, and a bad file can be silently overwritten                 HIGH
     Location: load_config() (140–147), save_config() (150–155),
               _maybe_show_privacy_notice() (792–802).

     load_config() does:
         cfg = dict(DEFAULT_CONFIG)
         with open(CONFIG_PATH, ...) as fh:
             cfg.update(json.load(fh))
     guarded only by `except (FileNotFoundError, json.JSONDecodeError,
     OSError): pass`.

     Two distinct failures follow from this:
       (i) If the file is *valid JSON but not a JSON object* — e.g. it was
           hand-edited into a list, a bare string, or a number —
           json.load() succeeds, so JSONDecodeError is never raised, and
           cfg.update(...) then throws TypeError or ValueError, which is
           NOT in the caught tuple. This propagates out of load_config(),
           out of Scriptorium.__init__, and crashes the whole application
           before the window ever appears. Confirmed by direct
           reproduction (not just inspection) — running the equivalent of
           load_config() against three sample payloads outside the
           project directory:
               input '[1, 2, 3]'       -> UNCAUGHT TypeError: cannot convert
                                          dictionary update sequence element
                                          #0 to a sequence
               input '"just a string"' -> UNCAUGHT ValueError: dictionary
                                          update sequence element #0 has
                                          length 1; 2 is required
               input '42'              -> UNCAUGHT TypeError: 'int' object
                                          is not iterable
       (ii) If the file is unreadable in a way that *is* caught (a
            genuinely malformed/truncated JSON document, or a permissions
            error), load_config() falls back to DEFAULT_CONFIG with no
            flag at all. On first run with the Claude backend,
            _maybe_show_privacy_notice() then sets privacy_ack and calls
            save_config(cfg), which writes DEFAULT_CONFIG straight over
            the broken file — destroying whatever API key and model choice
            were in it, with no warning that anything was lost.

     Remedy: validate that the loaded JSON is a dict before merging it,
     and mark the config as unreadable (refusing to overwrite it) for both
     failure modes instead of only the ones that happen to raise
     JSONDecodeError/OSError. See Fix 2.


2.3  Bug 3 — Truncated Claude responses produce a misleading error    MEDIUM
     Location: call_anthropic() (302–343).
     Detail: max_tokens is hard-coded to 4096 (line 313) and the response's
     stop_reason is never inspected. When Claude is cut off mid-JSON, the
     literal text handed to _extract_json() is a broken JSON fragment;
     _extract_json() then raises "The model did not return valid JSON.
     Try again, or lower the editing strength." — which sends the user
     toward the wrong fix (strength has nothing to do with it; the source
     text is too long for one 4096-token reply).
     Remedy: check payload.get("stop_reason") before parsing and raise a
     specific, actionable BackendError. See Fix 3.


2.4  Bug 4 — Placeholder masking swallows Markdown links and
     numeric citations                                               MEDIUM
     Location: _PLACEHOLDER_PATTERNS (441–447).
     Detail: `\[[^\[\]\n]+\]` matches any square-bracket content, so
     "[Name]" and "[1]" or "[the guide]" in "[the guide](url)" are treated
     identically. Confirmed by direct execution against the live regex
     (not the proposed one):
         input:   Dear [Name], see [the guide](https://example.com) and
                  footnote [1]. The sum is {amount} on {{Date}} and <Date>.
         current: ['[Name]', '[the guide]', '[1]', '{amount}',
                   '{{Date}}', '<Date>']
     "[the guide]" and "[1]" are not template slots — masking them either
     corrupts a Markdown link (the model sees an opaque sentinel where the
     link text belongs) or silently drops a numeric citation from the
     prompt entirely.
     Remedy: require a placeholder to start with a letter and refuse a
     following "(", which is enough to exclude both cases while keeping
     genuine slots like [Name] and [Recipient Name] intact — confirmed
     against the same sample:
         fixed:   ['[Name]', '{amount}', '{{Date}}', '<Date>']
     See Fix 4.


2.5  Bug 5 — Settings can be saved mid-request, mixing old and new
     credentials for a call already in flight                        LOW
     Location: process() worker (851–860), SettingsDialog.__init__ (555),
               SettingsDialog._save() (623–632).
     Detail: SettingsDialog is constructed with `self.cfg = cfg` — the
     exact same dict passed as self.cfg by open_settings() (1000-1001),
     not a copy. The worker closure created in process() reads
     `run_backend(system_prompt, masked, self.cfg)`, i.e. it consults the
     live dict at whatever moment its own code inside call_anthropic() /
     call_ollama() happens to read cfg.get(...). If the user opens Settings
     and clicks Save while a request is on the wire, the in-flight call can
     end up built from a partially-updated mix of old and new values (e.g.
     the new API key with the old model, or a backend switch mid-call).
     Remedy: snapshot cfg at the moment process() sends the request, so
     later Settings changes can only affect the *next* request. See Fix 5.


2.6  Bug 6 — Closing the window during a request can raise from a
     background thread                                                LOW
     Location: process() worker (851–860).
     Detail: the worker is a daemon thread that calls
     `self.after(0, self._on_success, ...)` (or _on_error) with no check
     that the window still exists. If the user closes Scriptorium before
     the request completes, this call can raise against an already-torn-
     down Tk root. It is a daemon thread so the process still exits
     cleanly, but it prints a noisy traceback and — because the exception
     happens after the actual HTTP call already succeeded or failed — the
     result is simply lost rather than shown anywhere.
     Note on limits: a `winfo_exists()` guard (as proposed in Fix 5) closes
     the common case where a child window/widget is gone but the Tcl
     interpreter is still alive; if the *entire* interpreter has already
     been finalised, winfo_exists() itself can raise. Wrapping the delivery
     call in a narrow try/except is therefore the more complete fix, and is
     what Fix 5 below does.


2.7  Residual risks (no code change proposed here)
     * The Claude API key remains plain text in scriptorium_config.json.
       .gitignore already excludes it from the repository. Moving it to
       Windows Credential Manager would be a real architectural change —
       out of scope per the "no major rewrites" brief; flagged for
       awareness only, as notes_001 already did.
     * self.undo_stack (and, after Feature 2 below, self.history) grow for
       the life of the session with no cap on undo_stack today. Not a
       correctness bug — a long session doing dozens of Clear/Import/
       Accept cycles will hold that many full-text copies in memory. Worth
       a `del self.undo_stack[:-N]`-style cap only if it is ever observed
       to matter in practice; not proposed as a fix here to avoid touching
       working code without a concrete symptom.
     * CTkOptionMenu will not show anthropic_model if a future config value
       is not in ANTHROPIC_MODELS (e.g. after a model ID is retired). Rare,
       and easy to soften later by inserting the current value at the
       front of the list if it is ever hit in practice.
     * audit_letter_conventions() scans the whole text for "Yours
       faithfully/sincerely", so a body that quotes the phrase in passing
       could in principle affect the advisory. The current "warn only when
       exactly one of the two is present" logic already keeps this quiet in
       the common case; tightening it to only the last non-empty line is
       optional polish, not a fix.

### Fix 2 — Never crash on, or silently overwrite, a bad config file
Insert at: scriptorium.py, replacing load_config() and save_config() (140–155).

def load_config():
    """Load scriptorium_config.json over the defaults.

    A missing file is normal (first run). A file that cannot be parsed, or
    that parses to something other than a JSON object (e.g. a list or a
    bare string), must NOT be treated as "use defaults and carry on" —
    that would let save_config() silently destroy the user's API key the
    next time anything triggers a save. Both failure modes are tagged with
    "_config_unreadable" so save_config() refuses to write.
    """
    cfg = dict(DEFAULT_CONFIG)
    try:
        with open(CONFIG_PATH, "r", encoding="utf-8") as fh:
            loaded = json.load(fh)
    except FileNotFoundError:
        return cfg
    except (json.JSONDecodeError, OSError) as exc:
        print(f"[warning] could not read config ({exc}); leaving the file untouched")
        cfg["_config_unreadable"] = True
        return cfg
    if isinstance(loaded, dict):
        cfg.update(loaded)
    else:
        print("[warning] config file is not a JSON object; leaving it untouched")
        cfg["_config_unreadable"] = True
    return cfg


def save_config(cfg):
    """Write the config file, unless load_config() flagged it as unreadable."""
    if cfg.get("_config_unreadable"):
        print("[warning] refusing to overwrite an unreadable config file")
        return
    try:
        to_write = {k: v for k, v in cfg.items() if not k.startswith("_")}
        with open(CONFIG_PATH, "w", encoding="utf-8") as fh:
            json.dump(to_write, fh, indent=2)
    except OSError as exc:
        print(f"[warning] could not save config: {exc}")

# Ordered longest-first so {{...}} is tried before {...}. Square brackets
# must look like a template slot ([Name], [Recipient Name]) — a letter
# immediately after "[", and not followed by "(" — so a Markdown link
# [label](url) or a numeric citation [1] is left alone.

    r"\[[A-Za-z][^\[\]\n]{0,40}\](?!\()",     # [Name], not [1] or [text](url)
    r"\{[A-Za-z][^{}\n]{0,40}\}",              # {amount}
    r"<[A-Za-z][A-Za-z0-9 _\-]{0,40}>",       # <Date>
]
_PLACEHOLDER_RE = re.compile("|".join(_PLACEHOLDER_PATTERNS))

4. THREE NEW FEATURES (usability, no architectural growth)
--------------------------------------------------------------------------------
Three independent past reviews (ChatGPT, Claude, Grok) have each proposed
live metrics, named presets and a change-summary/history aid, and none of
the three has been implemented yet — confirmed by grep: no `text_metrics`,
`PRESETS`, `summarise_changes` or `HistoryDialog` exists anywhere in the
current file. That three-for-three convergence, on a lightweight app with
no existing UI for any of them, is itself the strongest signal of which
features are worth doing next, so this report endorses the same shortlist
rather than inventing a fourth just to be different — but with fresh,
independently written implementations checked against the file's real
current line numbers, and (for the history feature) a lighter design than
previously proposed.

### Feature 1 — Live word/character metrics with a reading-time estimate
Rationale: the status bar currently shows only a raw character count of
the original, refreshed opportunistically. Anyone editing to a length
(a one-page letter, a tweet-length reply) benefits from a live word count,
and once a revision exists, how much longer or shorter it is.

Insert at: scriptorium.py, immediately after _tokenise() (392), before the
render_diff() definition (395):

def text_metrics(text):
    """Return (words, characters, reading_minutes) for a pane of prose.

    Words are Unicode word-characters, so surrounding punctuation does not
    inflate the count. Reading time assumes 200 words/minute, rounded up
    to whole minutes (0 for empty text), matching the estimate most
    writing tools show.
    """
    words = len(re.findall(r"\w+", text, flags=re.UNICODE))
    minutes = -(-words // 200) if words else 0  # ceiling division
    return words, len(text), minutes

MAX_HISTORY = 5


def add_history_entry(history, original, result):
    """Push a completed revision onto the front of an in-memory history list.

    Mutates `history` in place and trims it to MAX_HISTORY, so a long

    history.insert(0, {"original": original, "revised": result["revised"]})

    """Short, single-line menu label for one history entry."""
    preview = entry["original"].strip().replace("\n", " ")
    return (preview[:50] + "…") if len(preview) > 50 else (preview or "(empty)")
