1. EXECUTIVE SUMMARY
--------------------------------------------------------------------------------

Scriptorium v1.9 is in sound condition for a compact single-module desktop
application. The most dangerous defects recorded against v1.5 in notes_007 —
stale revisions being attached to the wrong source, in-flight results returning
after Reject, unsafe configuration replacement, truncated Claude replies, loose
placeholder matching, malformed Ollama model lists, non-UTF-8 import failures,
and incomplete model-JSON coercion — have largely been repaired.

The central revision state is now coherent:

  * each request has a monotonic _request_id;
  * Reject, Undo, Clear, Import and window close invalidate late callbacks;
  * last_result is paired with _result_source;
  * Accept, Copy revision and Export warn when the original has changed;
  * configuration is snapshotted for each worker;
  * placeholders are restored before display, storage or export.

No critical data-corruption defect was found in the current revision workflow.
The remaining issues are targeted robustness and UI-responsiveness matters. The
highest-value fixes are atomic configuration writes, validation of loaded
configuration values, defensive validation of backend response envelopes, and
moving Ollama model detection off the Tk event thread.

  1. Fix 1 — atomic configuration persistence.
  2. Fix 2 — validate loaded configuration values.

HIGH — Fix 1. Configuration writes are not atomic
-------------------------------------------------------------------------------

Location
  scriptorium.py, save_config(), lines 176–191.

Evidence
  save_config opens the live scriptorium_config.json with mode "w" before
  json.dump completes. A process termination, disk-full error or interrupted
  write can leave a truncated file. load_config correctly refuses to overwrite
  that malformed file later, but it cannot recover the API key and preferences
  already lost during the interrupted write.

Impact
  Loss of locally stored API credentials and settings. This is the only current
  finding with direct persistence/data-loss implications.

Targeted fix
  Serialise to a sibling temporary file, flush it, then use os.replace(), which
  atomically swaps the completed file on Windows. Clean up only the temporary
  file if the write fails.

Insertion point
  Replace save_config() at lines 176–191. os is already imported.

Ready-to-integrate snippet

    def save_config(cfg, *, force=False):
        """Persist configuration atomically without clobbering a bad file.

        A complete temporary JSON document is flushed before replacing the live
        file. Automatic saves still refuse to replace a configuration that was
        unreadable at startup unless the Settings dialog explicitly forces it.
        """
        if getattr(load_config, "unreadable", False) and not force:
            print("[warning] refusing to overwrite an unreadable config file")
            return False

        temporary_path = f"{CONFIG_PATH}.tmp"
        try:
            with open(temporary_path, "w", encoding="utf-8") as fh:
                json.dump(cfg, fh, indent=2)
                fh.flush()
                os.fsync(fh.fileno())
            os.replace(temporary_path, CONFIG_PATH)
        except (OSError, TypeError, ValueError) as exc:
            print(f"[warning] could not save config: {exc}")
            try:
                os.remove(temporary_path)
            except FileNotFoundError:
                pass
            except OSError:
                pass
            return False

        load_config.unreadable = False
        return True

Verification
  Save valid settings; confirm valid JSON. Mock json.dump to raise after writing
  partial data; confirm the original config remains byte-for-byte unchanged and
  only the temporary file is removed.

MODERATE — Fix 2. Valid but unsupported configuration values are not normalised
-------------------------------------------------------------------------------

Location
  load_config(), lines 149–173; toolbar variables at 813–855; process() at
  1017–1020.

Evidence
  load_config validates only that the root is a dictionary. Values such as
  {"default_mode": "Rewrite"}, null, or a list are merged unchanged. Process
  then indexes MODE_INSTRUCTIONS[mode] and STRENGTH_INSTRUCTIONS[strength]. An
  invalid toolbar value therefore raises KeyError in the worker and produces an
  "Unexpected error" rather than starting with a safe supported value. Invalid
  Boolean values such as the string "false" also become truthy through bool().

Impact
  A hand-edited or old config can produce inconsistent controls, unexpected
  processing failures, or safeguards being enabled contrary to the displayed
  value.

Targeted fix
  Normalise only enumerated and Boolean application values after cfg.update.
  Preserve free-form model names and API keys.

Insertion point
  Add normalise_config() immediately below DEFAULT_CONFIG. In load_config(),
  replace `return cfg` after cfg.update(loaded) with `return normalise_config(cfg)`.
  Also use it for the missing/unreadable-file returns if complete consistency is
  desired.

Ready-to-integrate snippet

    def normalise_config(cfg):
        """Return a copy containing only supported typed preference values."""
        clean = dict(cfg)
        choices = {
            "backend": ("anthropic", "ollama"),
            "default_mode": tuple(MODES),
            "default_strength": tuple(STRENGTHS),
            "default_role": tuple(ROLES),
            "default_tone": tuple(TONES),
            "default_diff_view": ("Clean", "Inline"),
        }
        for key, allowed in choices.items():
            if clean.get(key) not in allowed:
                clean[key] = DEFAULT_CONFIG[key]

        for key in ("privacy_ack", "protect_placeholders",
                    "check_letter_conventions"):
            if not isinstance(clean.get(key), bool):
                clean[key] = DEFAULT_CONFIG[key]
        return clean

Verification
  Load configs containing list/null/unknown values for each constrained key;
  confirm the window receives DEFAULT_CONFIG values and valid custom Ollama
  model tags remain unchanged.

MODERATE — Fix 4. Ollama Detect blocks the Tk event thread
-------------------------------------------------------------------------------

Location
  SettingsDialog._detect_models(), lines 739–752.

Evidence
  list_ollama_models performs urlopen(timeout=3) directly inside a button
  callback. The modal Settings window cannot repaint, close or respond during a
  slow DNS/socket/localhost condition for up to three seconds.

Impact
  A visible application freeze. Repeated clicks are currently possible until
  the blocking call begins/returns.

Targeted fix
  Disable Detect, perform only the network call on a daemon thread, and marshal
  the completed list back to the main thread. Keep all widget access on Tk's
  thread.

Insertion point
  Replace _detect_models() and add _finish_model_detection() immediately below
  it in SettingsDialog.

Ready-to-integrate snippet

    def _detect_models(self):
        """Detect local Ollama models without blocking the Settings window."""
        self.detect_btn.configure(state="disabled")
        self.ollama_status.configure(text="Detecting…")

        def worker():
            models = list_ollama_models()
            try:
                self.after(0, self._finish_model_detection, models)
            except (tk.TclError, RuntimeError):
                pass  # The dialog was closed before detection completed.

        threading.Thread(target=worker, daemon=True).start()

    def _finish_model_detection(self, models):
        """Apply a completed Ollama model list on Tk's event thread."""
        if not self.winfo_exists():
            return
        self._refresh_state()
        if not models:
            self.ollama_status.configure(
                text="No response from Ollama at localhost:11434 — is "
                     "'ollama serve' running?")
            return
        current = self.ollama_combo.get().strip()
        values = models if (current in models or not current) else [current] + models
        self.ollama_combo.configure(values=values)
        self.ollama_status.configure(text=f"Found {len(models)} model(s).")

Risk note
  Calling self.after from the worker follows the application's existing pattern.
  A queue polled by the main thread is stricter Tk isolation, but is a broader
  change. The guarded after is an incremental improvement appropriate here.

Verification
  Point OLLAMA_TAGS_URL temporarily at a delayed test endpoint; confirm Settings
  remains movable and closable and Detect stays disabled until completion.

MODERATE — Fix 5. A worker can attempt Tk scheduling after window destruction
-------------------------------------------------------------------------------

Location
  process() worker, lines 1023–1032; _on_close(), lines 1258–1261.

Evidence
  _on_close invalidates request ownership before destroy, which protects a
  callback already queued. It cannot stop a network worker from later executing
  self.after on a destroyed interpreter. The broad worker except then attempts a
  second self.after for the error path. This was only partly closed from
  notes_007 Bug 8.

Impact
  Usually a console traceback during shutdown rather than user-data loss. The
  daemon thread does not keep the process alive.

Targeted fix
  Centralise guarded scheduling so a failed success dispatch is not converted
  into a second failed error dispatch.

Insertion point
  Add _post_to_ui() immediately above process(). Replace all three worker
  self.after calls with this helper.

Ready-to-integrate snippet

    def _post_to_ui(self, callback, *args):
        """Queue a UI callback, returning False if shutdown has begun."""
        try:
            if not self.winfo_exists():
                return False
            self.after(0, callback, *args)
        except (tk.TclError, RuntimeError):
            return False
        return True

    # Inside worker():
    try:
        result = run_backend(system_prompt, masked, cfg_snapshot)
    except BackendError as exc:
        self._post_to_ui(self._on_error, request_id, str(exc))
    except Exception as exc:  # surface unexpected backend faults while alive
        self._post_to_ui(
            self._on_error, request_id, f"Unexpected error: {exc}")
    else:
        self._post_to_ui(
            self._on_success, request_id, original, ph_map, result)

Verification
  Start a deliberately delayed request and close immediately. Confirm there is
  no TclError/RuntimeError and normal successful/error callbacks still appear.

Ready-to-integrate snippet

    def _remember_for_undo(self, text, limit=50):
        """Store one distinct document snapshot in a bounded undo history."""
        if self.undo_stack and self.undo_stack[-1] == text:
            return
        self.undo_stack.append(text)
        if len(self.undo_stack) > limit:
            del self.undo_stack[:-limit]

  In clear_all(), optionally return early when both panes are already empty.

FEATURE 3 — Discoverable keyboard shortcuts for review actions
-------------------------------------------------------------------------------

Value
  Editing is faster without adding visible weight. Process/Import/Export already
  have shortcuts; Accept, Reject, Copy revision and Undo do not. A single binding
  helper keeps shortcut registration modular and avoids repeated lambdas.

Insertion point
  Add _bind_shortcuts() immediately above _build_toolbar(). Replace the three
  direct binds at lines 798–800 with `self._bind_shortcuts()`.

Ready-to-integrate snippet

    def _bind_shortcuts(self):
        """Register lightweight keyboard access to common review actions."""
        bindings = {
            "<Control-Return>": self.process,
            "<Control-i>": self.import_file,
            "<Control-s>": self.export_file,
            "<Control-Shift-A>": self.accept,
            "<Escape>": self.reject,
            "<Control-Shift-C>": self.copy_revision,
            "<Control-z>": self.undo,
        }
        for sequence, command in bindings.items():
            self.bind(sequence, lambda _event, action=command: action())

UI follow-up
  Amend button labels or add a short footer/help dialogue so shortcuts are
  discoverable, for example `Accept  (Ctrl+Shift+A)` and `Reject  (Esc)` where
  width permits. Do not intercept Ctrl+C/Ctrl+V in the editable Original pane.


6. ADDITIONAL OBSERVATIONS (NO IMMEDIATE PATCH REQUIRED)
--------------------------------------------------------------------------------

  * The single-file architecture is still proportionate at 1,270 lines. A broad
    module split would create churn without fixing a user-visible problem.
  * Storing the API key as plain text is clearly disclosed. Windows Credential
    Manager would improve security but adds platform-specific complexity and is
    better considered alongside packaging, not as an incidental fix.
  * Diff rendering is display-only; Accept/Copy/Export correctly use the clean
    `last_result["revised"]` value.
  * Placeholder protection correctly excludes numeric citations and Markdown
    links in v1.9.
  * The privacy notice is explicit and the backend configuration is snapshotted
    before a request, preventing Settings changes from re-labelling an in-flight
    request.
  * A live request is not cancellable at the HTTP/socket level; Reject only
    invalidates its eventual result. Given urllib and the lightweight design,
    this is an acceptable documented limitation.
  * Word import/export intentionally discards formatting. This matches the
    application's plain-text editing model and should not be presented as a
    round-trip-preserving Word editor.

  [ ] Each preset sets exactly four existing controls and does not lock them.
  [ ] Shortcuts fire once and preserve ordinary textbox Ctrl+C/Ctrl+V behaviour.


8. CONCLUSION
--------------------------------------------------------------------------------

Version 1.9 has resolved the earlier high-risk asynchronous state errors and is
now a credible, compact foundation. The next engineering pass should favour the
four bounded robustness patches at the head of this report. Of the lightweight
features, live counts offer the best value-to-code ratio, followed by named
presets and review shortcuts. Minimise-to-tray/autostart remains useful but is
best deferred until the executable packaging work establishes a stable Windows
launch and shutdown model.

No implementation should proceed without Mark's explicit authorisation.
