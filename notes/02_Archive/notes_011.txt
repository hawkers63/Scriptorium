1. EXECUTIVE SUMMARY
--------------------------------------------------------------------------------

Scriptorium v2.0 remains a sound compact application. Its high-risk revision
state defects are closed: requests are generation-stamped, stale results retain
their correct source, Reject/Undo/Clear/Import invalidate late callbacks, and
Accept/Copy/Export warn when the original has changed. The new atomic config
write is a worthwhile v2.0 improvement.

The review found no critical corruption bug in the editor state machine. It did,
however, confirm one HIGH repository/release consistency defect: the documented
v2.0 build depends on `scriptorium.spec`, but that file and the icon assets are
not tracked by Git. `update_repo.bat` stages only three hard-coded files and does
not stop on commit/push failure, so it can announce a successful update while
the remote repository is incomplete. At HEAD 94cad61 the tracked tree contains
only `.gitignore`, `README.md`, `Scriptorium.bat`, notes_001/002,
`requirements.txt`, `scriptorium.py`, and the example config; the spec is absent.

The most important application-level issue is a privacy-state disagreement for
an invalid backend string: the status bar says text stays local while
run_backend falls back to Claude. Configuration normalisation closes that hole
and also prevents invalid mode/strength values from crashing the Process button
callback before its worker thread is even created.

Finding totals in this review:

  HIGH      1
  MODERATE  8
  LOW       5
  DEFERRED  2 unconfirmed UI suspicions

Recommended implementation order:

  1. Repair repository synchronisation and commit the complete v2.0 source set.
  2. Normalise configuration values, especially backend/privacy state.
  3. Make save_config return success and keep Settings open on failure.
  4. Harden provider envelopes and timeout reporting.
  5. Move Ollama detection off the UI thread and guard post-close callbacks.
  6. Add the small Word-export and bounded-undo fixes.
  7. Add live counts, presets and review shortcuts as separate polish work.

MODERATE — Finding 2. Invalid backend values can falsely claim local privacy
-------------------------------------------------------------------------------

Locations
  load_config() 166–190; run_backend() 460–463; _refresh_status() 954–963;
  _maybe_show_privacy_notice() 968–978; build_system_prompt() 252–280.

Evidence
  run_backend sends every value except exact "ollama" to Claude. The status bar
  describes every value except exact "anthropic" as local Ollama. Therefore a
  hand-edited value such as "Ollama", "local", null or "" can display "stays on
  this machine", skip the privacy notice, and send via Claude if a key exists.
  Invalid mode/strength values also raise KeyError on the Tk thread before the
  worker starts.

Targeted fix
  Normalise enumerated and Boolean values immediately after config merge. Keep
  model IDs and the API key untouched. Make run_backend fail closed on any value
  that somehow bypasses normalisation.

Insertion point A
  Add immediately below DEFAULT_CONFIG, before load_config().

        Free-form API keys and model tags are preserved. An unknown backend
        becomes Anthropic so the status and privacy notice remain conservative.
        """

        choices = {
            "backend": ("anthropic", "ollama"),
            "default_mode": tuple(MODES),
            "default_strength": tuple(STRENGTHS),
            "default_role": tuple(ROLES),
            "default_tone": tuple(TONES),
            "default_diff_view": ("Clean", "Inline"),
        }
        for key, allowed in choices.items():
            if clean.get(key) not in allowed:
                clean[key] = DEFAULT_CONFIG[key]

        boolean_keys = (
            "privacy_ack", "protect_placeholders",
            "check_letter_conventions",
        )
        for key in boolean_keys:
            if not isinstance(clean.get(key), bool):
                clean[key] = DEFAULT_CONFIG[key]
        return clean

Insertion point B
  In load_config(), replace `return cfg` after `cfg.update(loaded)` with:

    return normalise_config(cfg)

Insertion point C
  Replace run_backend():

    def run_backend(system_prompt, user_text, cfg):
        """Dispatch to the explicitly selected backend or fail safely."""
        backend = cfg.get("backend")

MODERATE — Finding 3. Settings reports success even when persistence fails
-------------------------------------------------------------------------------

Locations
  save_config() 193–219; SettingsDialog._save() 788–797;
  Scriptorium._after_settings() 1281–1283.

Evidence
  save_config prints on failure and returns None both on success and failure.
  _save mutates the live cfg, calls save_config, calls on_save, then destroys the
  dialog. The status becomes "settings saved" even when no file was written.
  In the windowed executable the print warning is invisible.

Impact
  The current session uses unsaved settings, the dialog closes, and the next
  launch silently reverts. This is a direct in-memory/disk consistency defect.

Targeted fix and insertion points

  A. In save_config, return False from the unreadable/failure branches and True
     after os.replace succeeds:

    def save_config(cfg, *, force=False):
        """Persist configuration atomically and report whether it succeeded."""
        if getattr(load_config, "unreadable", False) and not force:
            return False
        tmp_path = f"{CONFIG_PATH}.tmp"
        try:
            with open(tmp_path, "w", encoding="utf-8") as fh:
                json.dump(cfg, fh, indent=2)
                fh.flush()
                os.fsync(fh.fileno())
            os.replace(tmp_path, CONFIG_PATH)
        except (OSError, TypeError, ValueError):
            try:
                os.remove(tmp_path)
            except OSError:
                pass
            return False
        load_config.unreadable = False
        return True

  B. In SettingsDialog._save(), build a candidate copy and commit it to memory
     only after persistence succeeds:

    def _save(self):
        """Validate and persist settings, keeping the dialog open on failure."""
        candidate = dict(self.cfg)
        candidate.update({
            "backend": self.backend_var.get(),
            "anthropic_api_key": self.key_entry.get().strip(),
            "anthropic_model": self.model_var.get(),
            "ollama_model": (
                self.ollama_combo.get().strip() or DEFAULT_OLLAMA_MODEL),
            "protect_placeholders": bool(self.protect_var.get()),
            "check_letter_conventions": bool(self.letters_var.get()),
        })
        candidate = normalise_config(candidate)
        if not save_config(candidate, force=True):
            messagebox.showerror(
                "Settings not saved",
                "Scriptorium could not write its configuration file. "
                "Your current settings have not been changed.",
                parent=self,
            )
            return
        self.cfg.clear()
        self.cfg.update(candidate)
        self.on_save()
        self.destroy()

  an error is visible, in-memory values remain unchanged, and the status does

    def _detect_models(self):
        """Detect local Ollama models without blocking the Settings window."""
        self.detect_btn.configure(state="disabled")
        self.ollama_status.configure(text="Detecting…")

        def worker():

        self.ollama_status.configure(text=f"Found {len(models)} model(s).")

MODERATE — Finding 7. Worker callbacks can be posted after application shutdown
-------------------------------------------------------------------------------

Locations
  process().worker() 1050–1061; _on_close() 1285–1288.

Evidence
  Request invalidation rejects a callback after it runs, but does not prevent
  the worker from invoking self.after on a destroyed Tcl interpreter. The broad
  except may then try a second self.after. In the windowed PyInstaller build this
  may appear as a post-exit traceback dialogue.

Incremental fix
  Centralise guarded UI posting and use try/except/else so a failed success post
  is not transformed into a second error post.

Insertion point
  Add _post_to_ui() directly above process(); replace process().worker().

    def _post_to_ui(self, callback, *args):
        """Attempt to queue a UI callback; return False during shutdown."""
        try:
            self.after(0, callback, *args)
        except (tk.TclError, RuntimeError):
            return False
        return True

    # Replacement worker body:
    def worker():
        try:
            result = run_backend(system_prompt, masked, cfg_snapshot)
        except BackendError as exc:
            self._post_to_ui(self._on_error, request_id, str(exc))
        except Exception as exc:  # defensive provider boundary
            self._post_to_ui(
                self._on_error, request_id, f"Unexpected error: {exc}")
        else:
            self._post_to_ui(
                self._on_success, request_id, original, ph_map, result)

Limitation
  Tkinter calls from worker threads are platform/interpreter-sensitive. The
  strict solution is a thread-safe queue polled by `after()` from the main
  thread, but that is a wider change. The helper is the smallest current-code
  improvement and must be tested on the packaged Windows build.

7. CONCLUSION
--------------------------------------------------------------------------------

Scriptorium's central editing state is now dependable; the next work should not
be a rewrite. The immediate priority is release integrity: ensure that the Git
repository genuinely contains the documented v2.0 packaging sources and that
the update helper cannot hide failures. Within the application, configuration
normalisation and truthful save reporting give the largest safety return for
the smallest change. Backend envelope/timeout checks, asynchronous Detect and
the Word-export boundary are independent, low-churn follow-ups.

For usability, live counts provide the best value-to-code ratio, with named
presets and review shortcuts close behind. Minimise-to-tray, autostart and
credential migration remain worthwhile later projects, but should not be mixed
into the focused robustness pass recommended here.

No implementation should proceed without Mark's explicit authorisation.
