1. Executive Summary
--------------------

Scriptorium v2.25 has a sound lightweight core. In particular, the current
single-result contract, explicit Accept/Reject boundary, fail-closed backend
dispatcher, bounded retry transport, atomic configuration writes, feature-gated
Word/tray support and deterministic fidelity checks are good load-bearing
decisions. The most valuable next work is not a structural rewrite. It is to
close a small number of state-boundary gaps where those good decisions are not
applied consistently at every UI or batch entry point.

Four findings should be treated as release-blocking for the next implementation
cycle:

  1. Settings can silently translate an invalid backend into Claude when an
     unrelated setting is saved, crossing the app's deliberate privacy boundary.
  2. Revision history loses ambiguity/safety evidence, can be mislabelled with
     controls that did not generate it, and can be overwritten by an in-flight
     request after the user explicitly restores an older entry.
  3. Valid but malformed JSON tone values can crash application start-up despite
     the normaliser's stated graceful-degradation contract.
  4. Batch mode can reprocess its own products, overwrite review files for
     equal-stem inputs, omit GUI-equivalent fidelity/letter warnings, and abort
     outside its promised per-file failure boundary.

The next tier comprises a non-modal export race, incomplete live-state
synchronisation after frozen-config migration, and silent omission of Word table
text. The remaining items are bounded hardening: a rare native clipboard handle
leak, malformed Ollama model metadata, error-response reading, and the narrow
single-instance start-up race.

Recommended implementation order
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

  P0 — privacy and evidence integrity
    F1 Settings backend selection; F2 immutable request context/history evidence;
    F3 history cancellation; F4 tone type safety.

  P1 — batch and document integrity
    F5 batch output/review parity; F6 modal/snapshotted diff export; F7 config
    migration synchronisation; F8 Word-table refusal or faithful extraction.

  P2 — lightweight features after P0/P1
    E1 selection-scoped processing (only after live-model calibration), E2
    change-by-change navigation, E3 provenance-aware review-record export.

  P3 — low-risk hardening and documentation
    F9 clipboard allocation, F10 Ollama detection, F11 HTTP error details, F12
    single-instance signalling, F13 version/documentation drift.

Three genuinely new, lightweight feature opportunities
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

  E1. Process selection
      An explicit context-menu/keyboard action sends only the selected passage,
      splices the returned passage back into an otherwise byte-identical full
      suggested revision, and still requires Accept. This lowers latency/cost for
      long documents without adding another pane or another result.

      Freshness check: process() currently always reads the whole Original at
      lines 3742–3752; the Original context menu only offers Copy/Paste at
      4023–4049; repository-wide searches found no selection-processing path in
      source, ROADMAP, MEMORY or numbered notes; it is not in the deferred list.

  E2. Change-by-change navigation
      Compact Previous/Next controls and keyboard shortcuts step through each
      non-equal diff opcode. This materially improves explicit review of long
      revisions while adding no model call and no persistence.

      Freshness check: render_diff() identifies changes but returns no anchors at
      lines 1617–1645, while the Suggested-revision header contains only its title
      and Clean/Inline toggle at 3251–3259. No "next change", "previous change"
      or navigator appears anywhere in source, roadmap, memory or notes, and the
      idea is not deferred.

  E3. Provenance-aware review record
      Add a third option to the existing Export diff dialogue: a self-contained
      Markdown record containing the immutable request settings, original,
      suggested revision, change summary, model ambiguities, deterministic review
      notices and an explicit "not accepted automatically" statement.

      Freshness check: the chooser currently exposes only unified/annotated
      formats at 2418–2468, and no review-record builder or provenance export was
      found in source, roadmap, memory or numbered notes. It extends an existing
      export seam and is not deferred.

None of these features changes the non-negotiable product contract: there is one
Original and one Suggested revision, and no result is applied without the user's
explicit Accept action. E1 is input-scope-adjacent to prompt behaviour and is
therefore gated on real backend calibration described in section 2.5; paper-only
reasoning is not sufficient for shipment.

2. Detailed Architectural Proposals
------------------------------------

2.1 Current architecture and safe extension seams
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Configuration seam
  DEFAULT_CONFIG (799–819), normalise_config (859–909), load_config (912–945)
  and atomic save_config (948–979) already form a clear boundary. New persistent
  state should be avoided for all three proposed features; transient request and
  review metadata belong in the existing in-session state/history only.

Backend seam
  call_anthropic/call_ollama (1409–1497) share run_backend (1500–1521) and the
  v2.25 response-reader retry transport (1315–1406). No proposed feature needs a
  third-party HTTP package or SDK. E1 reuses one ordinary non-streaming call.

Review seam
  render_diff/summarise_diff and the Markdown/HTML builders (1617–1783) already
  centralise comparison. E2 should return transient anchors from render_diff;
  E3 should reuse summarise_diff and the existing safe Markdown-fence helper.

Persistence seam
  Revision history is deliberately memory-only (2963–2982). Request provenance
  must stay there; it must never include the API key and must never be silently
  written to scriptorium_config.json. E3 writes content only after an explicit
  Export dialogue, which is already the product's persistence boundary.

Feature gates
  Word I/O and tray support already degrade explicitly when their optional
  packages are missing. None of E1–E3 needs a new dependency or feature gate.


2.2 Confirmed defects and targeted fixes
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

F1 — HIGH — Settings violates the fail-closed backend/privacy boundary

Evidence
  * normalise_config intentionally preserves a present invalid backend at
    881–890 so run_backend can refuse it at 1512–1521.
  * _refresh_status reports that invalid state honestly at 3445–3457.
  * Settings maps any unknown string to visible "Claude" at 2516–2518 and maps
    any unrecognised selection to "anthropic" at 2748.
  * A list or dict backend is even less safe for the dialogue: using it as a key
    in BACKEND_LABELS.get() raises TypeError before Settings opens.
  * If privacy_ack is already true, the cloud notice at 3594–3604 does not recur.

Failure
  A config with backend "Ollma" initially refuses to process, as designed. The
  user opens Settings only to change Always on top and clicks Save; the app then
  silently persists the Claude backend. That is a behaviour/privacy change not
  explicitly chosen by the user.

Targeted fix
  Show no selected segment for an invalid/non-string backend, display a concise
  repair message, disable both model groups and Save, then enable Save only after
  the user explicitly chooses Claude or Ollama. Remove every default-to-anthropic
  expression from Settings. Preserve run_backend's existing fail-closed rule.

State/config/performance
  No schema change. Only invalid configurations see the repair state. O(1).
  No prompt change and no model calibration required.

Verification gate
  Test invalid string, null, list and object backend values. Settings must open,
  show neither backend selected, make no network call, refuse Save, then persist
  only the backend explicitly clicked. Repeat with privacy_ack true.


F2 — HIGH — Completed revisions do not retain truthful request provenance

Evidence
  * process() reads live Mode/Strength/tones/Role for the prompt at 3771–3775.
  * those toolbar controls remain editable while busy.
  * _remember_for_history reads them again only after completion at 3857–3865.
  * cfg_snapshot promises mid-request settings affect the next request at 3785,
    yet _on_success reads live check_letter_conventions at 3832.

Failure
  Changing a control or applying a preset during a slow request labels the
  history entry with settings that did not generate it. A mid-request Settings
  change can also change whether the finished text is letter-audited.

Targeted fix
  Capture one non-secret request context before prompt construction, use its
  values to build the prompt, pass it through the worker callback, and use it for
  completion audits, history labels and E3 export. Store backend/model identifiers
  but never API credentials. Keeping controls enabled is then harmless and useful:
  the user can prepare the next request without corrupting this one's provenance.

State/config/performance
  One small dict for the active result and each of at most 50 in-memory history
  entries. No config key and no disk persistence. O(1). Prompt wording unchanged.


F3 — HIGH — History restoration drops review evidence and can be overwritten

Evidence
  * _on_success displays model ambiguities plus placeholder, fidelity,
    stale-source and letter warnings at 3811–3842.
  * _remember_for_history stores none of ambiguities, note or warnings at
    3849–3865.
  * _restore_from_history fabricates empty ambiguities/note and hides the banner
    at 4507–4511.
  * History remains enabled while busy; _restore_from_history does not call
    _invalidate_inflight(), so the still-current worker may overwrite the entry
    the user just chose.

Failure
  A revision originally flagged for a lost figure, URL, placeholder, quotation or
  genuine ambiguity appears warning-free after restoration. Separately, a late
  callback can replace the restored revision against the user's explicit choice.

Targeted fix
  Divide notices into durable review notices and the transient "Original changed
  while processing" message. Store model ambiguities, note, durable notices and
  request context in the bounded in-memory history entry. Restore them, but do not
  revive the transient stale-source message when Original has just been restored
  to the matching snapshot. Call _invalidate_inflight() before any restore edit.
  Rename the generic banner heading from "Ambiguities flagged" to "Review
  notices" when it contains deterministic audits as well as ambiguities.

State/config/performance
  Bounded by the existing 50-entry cap. No disk/config change. O(number of notice
  strings), normally tiny. No prompt change.


F4 — HIGH — Valid JSON with nested non-string tones can crash start-up

Evidence
  validate_tones says unrecognised data degrades gracefully at 508–517 but hashes
  each value at line 523. normalise_tone_config and normalise_preset catch only
  ValueError at 850–853 and 666–669. Direct probes reproduced TypeError for a list
  legacy tone and a dict inside preset tones.

Targeted fix
  Make validate_tones the real type boundary: accept the internal string/list/
  tuple forms, return an empty selection for other containers, and skip every
  non-string element before membership checks. Keep canonical order, duplicate
  handling, three-tone limit and hard conflicts unchanged.

State/config/performance
  No schema or behavioural change for valid configs. O(number of supplied tones),
  capped in normal use. No prompt calibration: malformed entries never reach the
  prompt, while valid prompt construction is byte-for-byte unchanged.


F5 — HIGH — Batch output and safety evidence are not equivalent to GUI review

Evidence
  * INPUT_DIR may equal OUTPUT_DIR. Generated *.revised.txt/*.diff.txt match the
    next scan's allowed suffixes at 4788–4791 and are reprocessed on a later run.
  * report.txt and report.md both write report.diff.txt at 4851, so one review
    report overwrites the other.
  * placeholder restoration warnings go only to batch_log.txt at 4845–4848;
    protected-content fidelity and letter-convention audits are never run.
  * os.makedirs and opening batch_log.txt sit outside error handling at
    4785–4797; load_config.unreadable is ignored; the output block catches only
    OSError although write_docx can raise ImportError/ValueError.
  * the stated contract at 4736–4742 says one bad file does not stop the batch and
    every revision has a review companion. Several paths violate that promise.

Targeted fix
  Reject equal real input/output directories; name review files from the complete
  input name (report.txt.diff.txt / report.md.diff.txt); share a pure
  collect_revision_notices() helper between GUI and batch; put all ambiguity,
  model note and deterministic warnings in each per-file review; abort rather than
  silently use defaults when config is unreadable; guard output/log preparation;
  and keep write_docx's ImportError/ValueError inside the per-file boundary.

State/config/performance
  No schema change. Each audit is linear in document size, already paid in the GUI
  and small beside a model call. No prompt change. Existing inputs are untouched.

Verification gate
  A future implementation session should use disposable fixtures (not the live
  notes/config): same input/output folder; same stem across .txt/.md/.docx; a
  pre-existing revised file; missing python-docx; illegal XML character; malformed
  config; placeholder loss; figure/URL change; letter mismatch; read-only output;
  and a successful mixed batch. Confirm unique paired outputs and exit code 1 for
  any failure without aborting later files.


F6 — MEDIUM — Diff-format chooser permits a nested-event state race

Evidence
  DiffExportFormatDialog has neither transient(master) nor grab_set() at
  2428–2435. wait_window() at 2464–2468 runs a nested event loop but does not make
  a dialogue modal. export_diff_file validates last_result before that dialogue,
  then dereferences mutable self.last_result later at 4009–4014.

Failure
  Reject/History or another state change behind the chooser can produce an
  AttributeError or export a different revision from the one the user intended.

Targeted fix
  Make the chooser transient/modal and snapshot source, revision, request context,
  note and notices before opening it. Use only the snapshots after either nested
  dialogue. This is also required by E3.

State/config/performance
  No persistent state, no prompt change and negligible cost.


F7 — MEDIUM — Frozen configuration migration leaves live state inconsistent

Evidence
  Migration reads utf-8 at 3560 although ordinary loading accepts utf-8-sig at
  926. After replacing self.cfg, it updates only five toolbar values at
  3582–3592. Imported user presets do not refresh preset_menu, imported
  always_on_top is not applied, and imported start_with_windows is written to JSON
  without creating the corresponding Run entry.

Targeted fix
  Read with utf-8-sig. Add one _apply_imported_config_to_live_ui() helper that
  updates the five controls, repopulates preset_menu, resets its command value,
  applies topmost, and explicitly reconciles the requested autostart entry. Do not
  apply launch-only visibility to the already-open window. If registry update
  fails, report it and do not claim JSON/Windows state agree.

Related consistency issue
  Settings itself saves JSON before set_autostart at 2761–2778, then commits the
  candidate and closes even if registry mutation fails. The warning is honest,
  so this is below F1, but the next Settings opening still shows requested rather
  than actual state. A small read-only get_autostart_command() helper should let
  Settings verify the transition and remain open on failure.


F8 — MEDIUM — Word import silently omits all table-cell text

Evidence
  read_docx joins document.paragraphs only at 1563–1571. python-docx does not
  include paragraphs inside tables in that collection. README advertises Word
  import generally and the UI gives no warning.

Targeted first fix
  Until reading-order-preserving table extraction is implemented and tested across
  the optional python-docx versions Scriptorium supports, refuse documents that
  contain tables with a precise explanation. A visible refusal is safer than
  sending a silently incomplete document to a model. A later enhancement may
  extract top-level paragraphs and tables in XML order, but should not guess at
  nested-table/list ordering in this incremental pass.

State/config/performance
  No schema change. One existing document.tables check. No prompt change.


F9 — LOW — Native clipboard allocation can leak one HGLOBAL

Evidence
  set_html_clipboard allocates html_handle at 1910 and text_handle at 1911 before
  entering its try/finally. If the second allocation fails, the first is never
  freed. Normal success and SetClipboardData transfer ownership are otherwise
  handled correctly.

Targeted fix
  Initialise both handles to None, allocate them inside the outer try, and free
  only non-null, non-transferred handles in finally.


F10 — LOW — Malformed Ollama model metadata can strand Detect

Evidence
  list_ollama_models appends any truthy name/model field then calls sorted() at
  1543–1552. Mixed strings/numbers or a dict can raise TypeError. It also omits
  http.client.HTTPException from its failure tuple. The Settings worker at
  2645–2652 has no final exception guard, so the button can remain disabled with
  "Detecting…" indefinitely.

Targeted fix
  Accept non-empty strings only, de-duplicate case-insensitively, catch the same
  transport family as the main backend, and make the worker always post a terminal
  callback. No config or prompt effect.


F11 — LOW — Reading a final HTTP error body can escape friendly error handling

Evidence
  exc.read() at 1359 occurs inside an except HTTPError handler. If that read raises
  TimeoutError or http.client.IncompleteRead, later sibling except clauses do not
  catch it. The final-error branch also does not explicitly close exc, whereas the
  retry branch closes at 1367.

Targeted fix
  Add a bounded _read_http_error_detail() helper that catches read/decode failures,
  returns a stable fallback, and closes the HTTPError in finally. No retry-policy
  or prompt change.

Evidence

Targeted fix
  Give _signal_existing_instance a short bounded retry (for example ten 50 ms

2.3 Feature E1 — Explicit selection-scoped processing
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

User experience
  When Original has a selection, its existing right-click menu gains "Process
  selection" and Ctrl+Shift+Enter invokes the same action. With no selection the
  command is disabled and the shortcut reports "select a passage first". The
  status says that only the selected passage is being sent. The full Suggested
  revision still appears in the existing right pane: prefix and suffix are copied
  locally and byte-for-byte unchanged around the returned selected passage.
  Accept remains the only action that changes Original.

Architecture
  Factor the body of process() into _begin_processing(scope). A scope is a small
  dict containing full_original, request_text, prefix, suffix and kind. Full mode
  supplies empty prefix/suffix; selection mode captures the three pieces from the
  Tk selection before starting the worker. Placeholder masking applies only to
  request_text. On success, restore those placeholders, assemble the full proposed
  revision locally, then run fidelity and letter audits against the full Original
  and full assembled revision. The unchanged exterior is therefore guaranteed by
  Python rather than requested from the model.

State
  Add scope to the immutable request context. _result_source remains the complete
  Original so stale-result checks, diff, copy, export, history and Accept need no
  semantic fork. No config key, no second result and no persistent selection.

Performance/privacy
  One ordinary backend call with a smaller body; local concatenation is O(n).
  Text outside the selection does not leave the machine even on Claude. The UI
  must say this plainly and also warn that the model cannot use unseen surrounding
  context.

Mandatory live-model calibration before shipment
  Although build_system_prompt() need not change, narrowing the user text changes
  what the model can infer. Run real calls through the configured Claude backend
  when credentials are available and through the Ollama model actually installed
  and loadable on this machine (do not assume llama3.1:8b). Use a fixed corpus with
  at least:

    * mid-sentence selections and leading/trailing punctuation;
    * pronouns whose antecedent is outside the selection;
    * negation, modality, hedges, quantities, dates, money and percentages;
    * quotations, URLs, paths, emails and every placeholder shape;
    * Markdown list items, headings, blank lines and boundary whitespace;
    * a selection that is already correct and one genuinely ambiguous fragment;
    * all modes, three strengths, roles, single tones and representative safe
      multi-tone combinations in both dominant orders.

  Pass only if every byte outside the selection is unchanged, protected inventory
  is preserved, no fact/certainty/scope is added, ambiguity is surfaced rather
  than guessed when context is missing, and the returned fragment splices without
  doubled/missing boundary whitespace. Record source, response, model tag and
  verdict. If either backend repeatedly guesses missing context, do not ship the
  feature merely with stronger prose instructions; keep it disabled until the UX
  provides an explicit context strategy that is itself calibrated.


2.4 Feature E2 — Change-by-change navigator
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

User experience
  Add compact "Prev", "1 / N" and "Next" controls in the Suggested-revision
  header, immediately to the left of Clean/Inline. Disable them when there is no
  active revision or no wording change. Ctrl+Alt+Left/Right (or F6/Shift+F6 after
  checking existing Windows conventions in a manual pass) cycles and scrolls the
  active change into view. A subtle underline/current-change tag must supplement,
  not replace, the existing green/red semantic colours.

Architecture/state
  Have render_diff return displayed (start, end) Tk index pairs for every non-equal
  SequenceMatcher opcode. Existing callers may ignore a return value, so this is a
  backward-compatible seam. Store _change_ranges and _change_cursor transiently.
  Centralise the three current rendering call sites (_on_success,
  _on_diff_view_change and _restore_from_history) through
  _render_active_revision(), and clear navigation in reject(). Clean-view pure
  deletions have a zero-width anchor; navigation still scrolls to the boundary
  without pretending adjacent text was deleted.

Config/performance/calibration
  No config, persistence, dependency, prompt or model calibration. The existing
  O(n) diff already produces the opcodes; storage is O(k) for k changed regions and
  each navigation action is O(1).


2.5 Feature E3 — Provenance-aware review-record export
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

User experience
  Add "Review record" beside Unified diff and Annotated prose in the existing
  Export diff dialogue. The saved Markdown starts with an explicit status:
  "Suggested revision — not accepted automatically". It then records generation
  time, backend/model, scope, Mode/Strength/Role/Tones, change summary, model note,
  all ambiguities and deterministic notices, followed by fenced Original and
  Suggested revision and the ordinary unified diff.

Architecture/state
  Reuse the immutable request context and durable notices from F2/F3. Snapshot all
  inputs before the modal chooser (also closing F6). Add one pure
  build_review_record() beside the existing Markdown builders. It must never
  include anthropic_api_key, environment data or any hidden prompt. History stays
  memory-only; a record is written only through the explicit save dialogue.

Config/performance/calibration

        """Return True when two paths identify the same directory.

    def _signal_existing_instance(attempts=10, delay=0.05):
        """Ask the running instance to show, tolerating its start-up window."""
        kernel32 = _kernel32()
        for attempt in range(attempts):
            handle = kernel32.OpenEventW(

  * Existing full-document prompts are byte-for-byte unchanged unless a separately

  * No automatic acceptance or persistent history is introduced.
  * No source text leaves the machine when Ollama is selected; invalid backend

Final recommendation
--------------------

Implement F1–F4 as one narrowly scoped state-integrity release, then F5–F8 as a
second batch/document-integrity release. E2 and E3 are safe candidates immediately
after those foundations because they do not touch model behaviour. E1 has the
highest day-to-day value, but its implementation must remain behind the explicit
live-model calibration gate: selection scope changes available context, and the
project's own v2.4/v2.11 history shows that meaning preservation cannot be trusted
from plausible prompt design alone.

Do not implement visible streaming, a module split, Credential Manager storage or
three simultaneous alternatives as part of this work. Their recorded product and
architecture decisions remain unresolved or explicitly deferred.
