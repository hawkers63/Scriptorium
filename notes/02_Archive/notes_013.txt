The implementation of multiple simultaneous tones is indeed feasible, as the current prompt architecture is already nearing the capability to support this feature. A prudent approach would be to avoid creating separate prompts for every possible combination. Instead, I propose treating tones as composable instructions, maintaining the selection as a concise ordered list, allowing the prompt to balance them according to the existing meaning-preservation rules.

**Recommendations:**  
I recommend the following parameters for tone selection:  
- A maximum of three tones per request  
- An explicitly ordered selection  
- The first tone designated as the dominant tone  
- The second and third tones serving as supporting characteristics  
- A minor conflict check for genuinely contradictory pairs  
- A compact toolbar control featuring a checkbox picker  

For instance:  
- Casual + Detailed  
- Professional + Empathetic  
- Direct + Constructive  
- Diplomatic + Assertive  
- Inspirational + Persuasive  
- Instructive + Friendly + Detailed  

The order of tones is significant. For example, 'Diplomatic + Direct' would imply a primarily diplomatic tone that is clear and direct, whereas 'Direct + Diplomatic' would indicate a primarily direct tone, softened by diplomatic elements. This approach facilitates useful variations without necessitating a combinatorial prompt table.  

**Rationale Against Merely Joining Tones into a String:**  
The current implementation issues a single generic instruction:  
- Steer the tone towards: concise.  

A simplistic multi-tone version might yield:  
- Steer the tone towards: casual, detailed.  

While this could function to a degree, it would leave excessive interpretation to the model. Several of the proposed tones describe distinct stylistic dimensions:  

| Dimension              | Tones                                   |
|-----------------------|-----------------------------------------|
| Register              | Casual, Professional                    |
| Detail and Length     | Concise, Detailed                       |
| Interpersonal Manner   | Friendly, Empathetic, Diplomatic       |
| Force and Certainty   | Direct, Assertive, Confident           |
| Purpose               | Instructive, Persuasive, Constructive, Inspirational |

This structure is beneficial, as tones from different dimensions combine naturally. For example, 'Casual + Detailed' is coherent because one regulates the register while the other governs depth. Some combinations within the same dimension can also be advantageous:  
- 'Direct + Diplomatic' implies clarity tempered by tact.  
- 'Assertive + Empathetic' conveys firmness while acknowledging the reader.  
- 'Professional + Friendly' suggests a polished yet approachable tone.  

The only evidently contradictory pair within the proposed set is:  
- 'Concise + Detailed'.  

Even this combination could be interpreted as “information-dense without unnecessary wording”; however, it may lead to confusion for both users and models. Consequently, I would recommend initially prohibiting this combination and providing a brief explanation.

**Function to Validate Tones:**  
```python
def validate_tones(tones):
    """Return a normalised tone list or raise ValueError for a conflict.

    Tone order is preserved because the first selection is treated as dominant.
    Duplicate, blank and keep-original entries are removed. No more than three
    tones are accepted, ensuring the model receives a clear stylistic direction.
    """
    normalised = []
    for tone in tones:
        if tone in ("", "(keep original)") or tone in normalised:
            continue
        if tone not in TONE_INSTRUCTIONS:
            continue
        normalised.append(tone)

    if len(normalised) > MAX_SELECTED_TONES:
        raise ValueError(
            f"Choose no more than {MAX_SELECTED_TONES} tones.")

    selected = set(normalised)
    for pair, message in TONE_CONFLICTS.items():
        if pair.issubset(selected):
            raise ValueError(message)

    return normalised
```

This function should serve as the sole validation boundary for:  
- Configuration loading  
- Preset application  
- The tone-selection dialogue  
- Prompt construction  

It is imperative not to maintain separate validation logic across each UI method.  

**Prompt Construction:**  
Please amend the tone argument in `build_system_prompt()` to accommodate tones. Replace the existing tone block in `[scriptorium.py](C:\\Scriptorium\\scriptorium.py)` with the following:

```python
def build_tone_instruction(tones):
    """Return a bounded prompt instruction for an ordered tone combination.

    The first tone is dominant. Later tones refine it rather than competing
    equally. Every instruction remains subordinate to meaning preservation.
    """
    tones = validate_tones(tones)
    if not tones:
        return ""

    descriptions = [
        f"- {tone}: {TONE_INSTRUCTIONS[tone]}."
        for tone in tones
    ]

    if len(tones) == 1:
        relationship = (
            f"Use {tones[0]} as the target tone."
        )
    else:
        supporting = ", ".join(tones[1:])
        relationship = (
            f"Use {tones[0]} as the dominant tone. Blend in {supporting} as "
            "supporting characteristics. If the characteristics compete, "
            f"preserve {tones[0]} as the priority."
        )

    return (
        "\n- Tone guidance:\n"
        f"  {relationship}\n"
        + "\n".join(f"  {line}" for line in descriptions)
        + "\n  Tone guidance may affect wording, rhythm and presentation only. "
          "It must not introduce facts, increase certainty, invent feelings, "
          "create commitments or alter the author's intended meaning."
    )
```

Add the following helper function directly below `validate_tones()`:

```python
def normalise_tone_config(cfg):
    """Migrate and validate the configured default tone selection.

    Existing installations using the singular default_tone key will continue 
    to function as before. The returned dictionary will always contain default_tones.
    """
    clean = dict(cfg)

    stored = clean.get("default_tones")
    if isinstance(stored, str):
        stored = [stored]
    elif not isinstance(stored, list):
        legacy = clean.get("default_tone", "(keep original)")
        stored = [] if legacy == "(keep original)" else [legacy]

    try:
        clean["default_tones"] = validate_tones(stored)
    except ValueError:
        clean["default_tones"] = ["Concise"]

    clean.pop("default_tone", None)
    return clean
```

```python
class TonePickerDialog(ctk.CTkToplevel):
    """Facilitates an ordered selection of up to three compatible writing tones."""

    def __init__(self, master, selected, on_apply):
        super().__init__(master)
        self.on_apply = on_apply
        self.selected_order = list(validate_tones(selected))
        self.variables = {}

        self.title("Choose tones")
        self.geometry("420x540")
        self.resizable(False, False)
        self.transient(master)
        self.grab_set()

        ctk.CTkLabel(
            self,
            text="Choose up to three tones",
            font=ctk.CTkFont(size=16, weight="bold"),
        ).pack(anchor="w", padx=18, pady=(16, 2))

        ctk.CTkLabel(
            self,
            text=(
                "The first selected tone is dominant. Subsequent tones provide "
                "supporting characteristics."
            ),
            wraplength=380,
            justify="left",
            text_color="gray65",
        ).pack(anchor="w", padx=18, pady=(0, 10))

        tone_frame = ctk.CTkScrollableFrame(self, height=350)
        tone_frame.pack(fill="both", expand=True, padx=16, pady=4)

        for tone in TONE_INSTRUCTIONS:
            variable = tk.BooleanVar(value=tone in self.selected_order)
            self.variables[tone] = variable
            ctk.CTkCheckBox(
                tone_frame,
                text=tone,
                variable=variable,
                command=lambda name=tone: self._toggle_tone(name),
            ).pack(anchor="w", padx=8, pady=5)

        self.status_label = ctk.CTkLabel(
            self, text="", text_color="gray65")
        self.status_label.pack(anchor="w", padx=18, pady=(4, 0))

        buttons = ctk.CTkFrame(self, fg_color="transparent")
        buttons.pack(fill="x", padx=16, pady=14)

        ctk.CTkButton(
            buttons,
            text="Clear",
            width=90,
            fg_color="gray30",
            command=self._clear,
        ).pack(side="left")

        ctk.CTkButton(
            buttons,
            text="Cancel",
            width=90,
            fg_color="gray30",
            command=self.destroy,
        ).pack(side="right", padx=(8, 0))

        ctk.CTkButton(
            buttons,
            text="Apply",
            width=90,
            command=self._apply,
        ).pack(side="right")

        self._refresh_status()
    
    def _toggle_tone(self, tone):
        """Track selection order and limit selections to the defined maximum."""
        selected = bool(self.variables[tone].get())

        if selected:
            if tone not in self.selected_order:
                if len(self.selected_order) >= MAX_SELECTED_TONES:
                    self.variables[tone].set(False)
                    messagebox.showinfo(
                        "Tone limit",
                        f"Choose no more than {MAX_SELECTED_TONES} tones.",
                        parent=self,
                    )
                    return
                self.selected_order.append(tone)
        elif tone in self.selected_order:
            self.selected_order.remove(tone)

        self._refresh_status()

    def _refresh_status(self):
        """Display the current count and dominant-tone order."""
        count = len(self.selected_order)
        if not self.selected_order:
            description = "Original tone will be preserved."
        else:
            description = " → ".join(self.selected_order)
        self.status_label.configure(
            text=f"{count} of {MAX_SELECTED_TONES} selected: {description}"
        )

    def _clear(self):
        """Clear all selected tones while preserving the source's original tone."""
        self.selected_order.clear()
        for variable in self.variables.values():
            variable.set(False)
        self._refresh_status()

    def _apply(self):
        """Validate the selection and return it to the application."""
        try:
            tones = validate_tones(self.selected_order)
        except ValueError as exc:
            messagebox.showwarning(
                "Incompatible tones", str(exc), parent=self)
            return

        self.on_apply(tones)
        self.destroy()
```

### A Few Cautions

- Avoid instructing the model to “act as” or “adopt the persona of” a lawyer, engineer, or teacher. Scriptorium should apply a writing context rather than claim professional expertise.
- The role of Lawyer should never imply legal advice or introduce legal interpretation.
- The Engineer role must not generate technical conclusions absent from the source material.
- The Journalist role must not fabricate attribution or corroboration.
- The Copywriter and Persuasive roles should refrain from amplifying unsupported claims.
- The Teacher, Educator, and Instructive roles must not create facts or steps that were not originally present.
- The Detailed role must retain and organise detail without manufacturing it.

### Proposed Role Names for Consideration

A more cohesive menu structure may be achieved through the consolidation of roles:

- **Creative and Creative Professional**: Retain as *Creative Professional*.
- **Legal & Compliance and Lawyer**: Retain both only if:
  - *Lawyer* focuses on legal drafting.
  - *Legal & Compliance* centres on policies, controls, and obligations.
- **Educator and Teacher**: Retain both only if:
  - *Educator* encompasses explanatory or curriculum material.
  - *Teacher* pertains to direct communication with learners.
- **Designer and Graphic Designer**: Retain both only if:
  - *Designer* is broader and user-centred.
  - *Graphic Designer* explicitly addresses visual communication.
- **Writer, Story Writer, and Novelist**: Differentiate between general prose, short-form narrative, and long-form fiction.

Although the current **CTkOptionMenu** can accommodate an extensive role list, approximately 25 entries may become unwieldy. Transitioning to a **CTkComboBox** with predefined role values would represent a modest improvement, enabling users to type the initial letters. If this is implemented, it is advisable to validate the input against **ROLE_INSTRUCTIONS** prior to processing, rather than silently disregarding an invalid entry as if there were no role.

### Combinatorial Range Analysis

With 14 tones, the combinations are as follows:

- **Single tones**: 14 combinations.
- **Two-tone combinations**: 91 unordered combinations.
- **Three-tone combinations**: 364 unordered combinations.

This yields a total of 469 possible non-empty selections before considering the order.

If order is significant:

- **One tone**: 14.
- **Ordered pairs**: 182.
- **Ordered triples**: 2,184.

This already provides more variation than users are likely to require. There is no justification for allowing four or more tones, as exceeding three can dilute, contradict, and complicate user expectations.

The combination of model, editing mode, strength, role, and tone already creates a vast behavioural space. Given three modes, three strengths, approximately 25 roles, and hundreds of tone combinations, limiting to three tones serves as a usability safeguard rather than an arbitrary restriction.

- Whether “Detailed” resulted in elaboration.
- Whether “Persuasive” strengthened factual claims.
- Whether dominant-tone ordering produced a noticeable difference.

Final Assessment:
The implementation of multiple tones is warranted. This concept aligns particularly well with Scriptorium as the existing architecture already delineates:
- Mode: the type of edit to perform.
- Strength: the extent of the edit.
- Role: the writing context.
- Tone: the desired auditory quality of the result.

The optimal approach includes:
- Storing tones as an ordered list.
- Limiting to a maximum of three tones.
- Designating the first tone as dominant.
- Providing explicit bounded instructions for every tone.
- Initially prohibiting only genuinely confusing combinations.
- Employing a compact picker rather than expanding the toolbar with multiple menus.
- Maintaining migration from the existing **default_tone** string.
- Updating presets to incorporate tone lists.
- Testing for meaning preservation prior to expanding the conflict rules.

I would advocate implementing two-tone support first in the UI while utilising a data model that permits three tones. This would facilitate the desired *Casual + Detailed* behaviour with a limited initial calibration surface. Once the two-tone matrix is reliable, increasing the picker limit from two to three can be accomplished with a simple configuration change, rather than necessitating another structural revision.
